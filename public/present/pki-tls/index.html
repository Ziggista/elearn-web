Part 1 · Crypto basics

Symmetric encryption: one shared key

🔐

Like a safe with a combination

The same key locks and unlocks. Fast enough to encrypt everything: web pages, SQL queries, file transfers. (AES)

📨

The problem

How do we agree on the combination? If I email it to you, anyone reading the email has it too.

Symmetric crypto does almost all the real work, but it has a key-sharing problem. Public-key crypto is the fix, which is next.

Part 1 · Crypto basics

A key pair: hand out padlocks, keep the key

🔓

Public key

An open padlock. Give it to anyone. If it leaks, nothing bad happens.

🗝️

Private key

The only key that opens that padlock. Never leaves the server. If it leaks, anyone can pretend to be you.

The private key is the crown jewel. 👑

Algorithms you'll see: RSA (2048/3072-bit) and ECDSA (e.g. P-256). Both fine; no need for the maths. Everything else in this session depends on the private key staying private.

Part 1 · Crypto basics

A key pair does two jobs

JobHowProves
EncryptAnyone locks with your public key. Only your private key unlocks.Only you can read it
SignYou sign with your private key. Anyone checks with your public key.It came from you and wasn’t changed

Signing is a wax seal 🕯️ Anyone can check it. Only you can make it. Certificates run on signing.

Signing is the important one for the rest of today. A CA signing a cert is the CA saying "I checked, this key belongs to this name."

One does not simply

🧙‍♂️

email the .pfx

A .pfx bundles the certificate with its private key. Emailing it is handing out the crown jewel. We come back to this in Part 4.

Part 1 · Crypto basics

Hashes: a fingerprint for data

SHA-256("hello") = 2cf24dba5fb0a30e26e83b2ac5b9e29e… SHA-256("hello!") = ce06092fb948d9ffac7d1a376e404b26…

Same in, same out

Every time, on every machine.

Tiny change, totally different

One character flips the whole hash.

One way

You can’t get the data back from it.

You’ve seen these as cert thumbprints in IIS. Avoid MD5 and SHA-1.

Signatures sign the hash of the data, not the data itself. Thumbprints are hashes of the whole certificate.

Part 2 · Certificates

A certificate is an ID card for a public key

FieldExample
Subject Alternative Namesapp.rrc.qld.gov.au, app01.rrc.local ← the names it’s valid for
IssuerThe CA that signed it
Valid from / to2026-03-01 → 2026-09-17
Public keyRSA 2048 / ECDSA P-256
SignatureThe issuer’s seal over all of the above

Not in it: the private key. That lives separately on the server.

How does a browser know a public key really belongs to app.rrc.qld.gov.au and not an attacker? Someone trusted vouches for it, the way a government vouches for a driver's licence. That vouching is the certificate.
🧑‍💻☕

Browsers ignore the CN.
Only the SAN counts.

Change my mind.

Someone always says "but the CN is right". Modern browsers stopped looking at the Common Name years ago. If the name isn't in the SAN list, it fails.

Part 2 · Certificates

The chain of trust

🏛️

Root CA

Self-signed. Offline. ~20 years. Pre-installed in your trust store.

→
🏢

Intermediate CA

Does the day-to-day signing.

→
🖥️

Your server cert

On IIS, Apache, SQL…

The server must send its cert + the intermediate. The client already has the root.

The client follows signatures up the chain until it hits a root it trusts. Windows, browsers, Java and Linux each have their own trust store. Missing intermediate is the most common server-side mistake.
😎

Chrome: “Missing intermediate? I’ll just go fetch it.”

😭

Java, PHP, curl: PKIX path building failed

“It works in Chrome” proves nothing.

Browsers paper over a missing intermediate by fetching it. Most other clients don't. Always serve the full chain.

NamesReal public domains we ownAnything, incl. rrc.local
Use forPublic, phones, vendors, SaaSInternal sites, server-to-server, SQL, LDAPS

If anything outside our domain-joined fleet must trust it, it needs a public cert.

Phones, vendors, SaaS, Linux boxes and Java apps won't trust the internal CA unless told to. Mention how to request each kind of cert here.

Part 3 · TLS

TLS gives you three things

🙈

Confidentiality

Nobody in between can read it.

🧾

Integrity

Nobody can change it unnoticed.

🪪

Authentication

You’re talking to the real server.

Under HTTPS, SQL Server, LDAPS, SMTP, RDP, WinRM, APIs and most SaaS integrations. “SSL” is just the old name.

Authentication is the one people forget, and the one that "fixes" like TrustServerCertificate throw away.

Part 3 · TLS

What happens when a client connects

1
Client → Server

“Hello. I speak TLS 1.3 / 1.2. I want app.rrc.qld.gov.au.”

2
Server → Client

“Here’s my cert + intermediate, and proof I hold the private key.”

3
Client

Checks name, dates, chain, revocation. Any fail = stop.

4
Both

Agree a session key without ever sending it (ECDHE).

5
Both

Everything else is fast symmetric encryption. 🔒

Key insight: public-key crypto is only used at the start to prove identity and agree a key. Then symmetric crypto from Part 1 does the heavy lifting. Fresh key per session = forward secrecy.

Part 3 · TLS

Every cert error is one of four checks

🏷️

Name

Is the name I used in the SAN? Not by IP, short name or alias.

📅

Dates

Not expired? Is the server clock right?

⛓️

Chain

Leads to a root I trust? Intermediate sent?

🚫

Revocation

Not cancelled? Can I reach the CRL/OCSP URL?

Work out which one failed. The fix is usually obvious.

This is the slide to remember. It's 90% of diagnosis.
Renew the cert now
Wait, it’s not due till Saturday
😰

Every sysadmin, every renewal cycle

Renew early, and know when every cert expires. With lifetimes shrinking (coming up), this choice comes round far more often.

Part 4 · Our servers

File formats: one rule

✅ Public, share freely

.cer .crt .p7b .csr

🛑 Contains a private key

.pfx .p12 .key (and some .pem)

If it has a private key in it, it’s a password.

Don’t email it, share it, commit it or ticket it. Best of all: generate the CSR on the server so the key never travels.

Send a pfx password by a different channel from the file. Check .pem files for "BEGIN PRIVATE KEY" before sharing.
🙅
TrustServerCertificate=True
😏👉
Put a proper internal-CA cert on the SQL Server
TrustServerCertificate keeps encryption but throws away authentication. It's locking your car and leaving the key in the door. Same goes for curl -k, PHP verify_peer false, Python verify=False and Java trust-all managers.

Recap

Five things to remember

1

Public key is public. Private key is a secret, and so is any .pfx or .key.

2

A cert is an ID card for a public key, signed by a CA we trust.

3

TLS uses certs to prove identity and agree a key, then encrypts fast.

4

Every error is name, date, chain or revocation.

5

Never fix a cert error by turning checking off.
