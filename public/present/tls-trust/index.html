What TLS is

A sealed envelope, delivered to a checked address

✉️

Confidentiality

Opaque envelope. Eve sees noise.

🧷

Integrity

Tamper seal. Any change is detected.

🪪

Authentication

The address was checked against ID.

Encrypting a chat with Hank protects nothing.

This is the key idea of the session. People think TLS = encryption. But a perfectly encrypted connection to the wrong server is useless. The rest of the deck is about how Clint knows it's really talking to Seb.

The trust problem

“Hi, I’m Seb.” Anyone can say that.

🖥️🔑

Real Seb

Has a key pair. Hands out the public key, keeps the private key on the server.

😈🔑

Hank

Generates a key pair too, in 2 seconds, and also says “I’m Seb, here’s my public key.”

Clint has never met Seb. Clint needs someone already trusted to vouch for Seb.

Public keys are just numbers. Nothing about a public key says who it belongs to. That's the gap certificates fill.

Enter Cash

Cash the CA is a passport office

1
Seb applies

Sends the public key and the name wanted (a CSR). Keeps the private key.

2
Cash checks

Seb proves control of app.council.qld.gov.au (DNS record or web file). Hank can’t.

3
Cash signs

“This public key belongs to app.council.qld.gov.au until 17 Sep.” Signed with Cash’s private key.

🪪

That signed statement is Seb’s certificate: an ID card for Seb’s public key.

Our internal CA does the same job for corp.local names, except the "proof" is that the request comes from a domain-joined machine or an admin.

Windows, macOS, browsers and Java ship with a few hundred audited roots. Group Policy adds our internal CA to domain PCs. Break any link and Clint walks away.

This is the whole of "trust" in one slide. In practice there's an intermediate between Cash's root and Seb, and Seb has to send it. Same idea, one more link.
😈 Hank: Hi Clint, it’s me, Seb 👋
🧑‍💻 Clint: Cool. ID please.
😈 Hank: Here’s my certificate. I signed it myself.
🧑‍💻 Clint: Sir, this is a self-signed certificate. 🚪
A self-signed certificate is someone vouching for themselves. That's exactly what Clint can't accept from a stranger.

The handshake

How Clint and Seb start talking securely

🧑‍💻Clint
🖥️Seb

1 · Hello. I want app.council.qld.gov.au, I speak TLS 1.3. Here’s my half of the key exchange.

2 · Hello. My half of the key exchange, my certificate + intermediate, and a signature with my private key.

3 · Clint checks name, dates, chain, revocation, and Seb’s signature. ✅

4 · Both compute the same shared secret. It is never sent.

5 · 🔒 Encrypted conversation with fast symmetric keys.

Five steps, one round trip in TLS 1.3. The next few slides zoom in on steps 2, 3 and 4.

Step 2 · Seb proves it’s really Seb

A certificate can be copied. A signature can’t.

📄

The certificate is public

Anyone, including Hank, can download Seb’s certificate and send it.

✍️

The signature is the proof

Seb signs this exact handshake with the private key. Only the real Seb can.

Hank with a copied cert gets stuck right here. That’s why the private key is the crown jewel. 👑

If the private key leaks, Hank can be Seb. Remember this for the save now, decrypt later section at the end.

Step 3 · Clint checks

Four checks, any fail = stop

🏷️

Name

Is app.council.qld.gov.au in the SAN?

📅

Dates

Is it valid today?

⛓️

Chain

Does it lead to Cash in my trust store?

🚫

Revocation

Has Cash cancelled it?

Then Clint verifies Seb’s signature with the public key from the cert. Pass = “I’m talking to the holder of Seb’s private key, and Cash says that’s app.council.qld.gov.au.”

Every certificate error your users see is one of these four failing. Clicking through a warning, curl -k or TrustServerCertificate=True skips them, which hands the connection to Hank.

Step 4 · A secret that’s never sent

Key exchange, explained with paint

🧑‍💻 Clint

Shared: yellow

Secret: red

Sends: yellow+red

👂 Eve sees
yellow, orange, green

Can’t un-mix paint

🖥️ Seb

Shared: yellow

Secret: blue

Sends: yellow+blue

Each adds their own secret to what they received. Both get yellow + red + blue. Same colour, never transmitted.

This is ECDHE, Elliptic-Curve Diffie-Hellman Ephemeral. "Ephemeral" means the secret colours are picked fresh for every connection and thrown away afterwards. Hold onto that word for the last section.

What if Hank tries?

Every trick hits a check

😈 Hank’s moveWhat stops Hank
Answers with a self-signed cert⛓️ Chain check
Uses a real cert for a name Hank owns🏷️ Name check
Copies Seb’s real certificate✍️ Can’t make Seb’s signature
Changes traffic after the handshake🧷 Integrity check, connection dropped
Records everything for later🤔 Encrypted noise… for now
The last row is the cliffhanger. Recording is cheap and passive. What happens if Hank gets something later that Hank doesn't have today?

What if Hank tries? · middlemen

Middlemen: why the checks exist

😈

Hank (malicious)

Rogue Wi-Fi, ARP spoofing, DNS poisoning, a hacked switch. They can see the traffic, but can’t produce a trusted cert for our server.

🛂

Ours, on purpose

Load balancers, reverse proxies, TLS inspection. They hold a key + cert the client trusts, so they move where the cert lives.

TLS makes middlemen harmless only if the client checks the certificate.

If outbound HTTPS from a server fails with a chain error, check whether something in the path re-signs traffic before blaming the vendor. Java and Linux tools won't trust our internal CA unless we add it.

Our internal CA

1

CN (Common Name) is the old “name” field. Browsers stopped using it for matching years ago.

2

SAN is the list Clint actually checks. If the name isn’t there, it fails, even if the CN is right.

3

Put every name people and systems use in the SAN: FQDN, alias/CNAME, load-balancer name.

4

Still set CN to the main name for humans and old tools.

Wildcards (*.corp.local) only cover one level and put the same key on every server that uses them, so prefer per-service SANs. Avoid short names (app01) and IP addresses in the SAN unless something genuinely connects that way.
🧑‍💻☕

Browsers ignore the CN.
Only the SAN counts.

Change my mind.

Someone always says "but the CN is right". It doesn't matter: name not in the SAN = name check fails.

What goes in Seb’s ID

What an internal server certificate needs

ItemWhat “right” looks like
🏷️ NamesEvery DNS name in the SAN; CN = the main one
🎯 PurposeEKU includes Server Authentication
🔑 KeyRSA 2048+ (or ECDSA P-256), made on the server, non-exportable
🏛️ IssuerOur internal CA, via the right template (e.g. Web Server)
⛓️ TrustClients trust our root: GPO for Windows; by hand for Java, Linux, appliances
🚫 RevocationClients can reach the CRL / AIA URLs in the cert
📅 LifecycleExpiry in the CMDB, owner named, renewal reminder set
Use this as the checklist when you raise a cert request with the PKI admins, and when you check a cert someone else installed. If any row is wrong, Clint will eventually complain.

What goes in Seb’s ID

Server or client: what the ID is for

🖥️

Server Authentication

EKU 1.3.6.1.5.5.7.3.1

“I am Seb.” Proves a server’s identity: IIS, SQL Server, RDP, LDAPS, Tomcat.

🧑‍💻

Client Authentication

EKU 1.3.6.1.5.5.7.3.2

“I am Clint.” Proves a client’s identity: Wi-Fi/VPN machine certs, API clients in mutual TLS.

🤝

Mutual TLS: Seb shows ID to Clint and asks Clint for ID. A server cert needs Server Auth; a client-only cert on IIS will be rejected.

Extended Key Usage (EKU) says what a certificate may be used for. Clients check it as part of accepting the cert. The AD CS Computer template includes both client and server auth, which is why machine certs sometimes "work" on a server; for services, use the proper Web Server template with the right names. Key Usage (digital signature, key encipherment) is the lower-level version of the same idea.

Seb is an IIS site

Seb applies to Cash

1
Make key + CSR

On the IIS server: certlm.msc custom request, or certreq -new app.inf app.req. Key not exportable. Every name in the SAN.

2
Send to Cash

Only the .req goes to the PKI admins. The private key stays on Seb.

3
Cash signs

AD CS issues it from a template (e.g. Web Server) and returns a .cer.

4
Seb pairs it

certreq -accept app.cer on the same server. Key icon = ID + key matched.

5
Show the ID

This is slide 9 (Cash the passport office) with real tools. If the key icon is missing, the cert was accepted on a different server from the one that made the request. Make a new request; don't export a key from elsewhere.

Seb is a Tomcat app

Java keeps Seb’s ID in a wallet

👛

Keystore = Seb’s wallet

Seb’s private key + certificate + Cash’s cert. conf/app.p12, password in server.xml. Secret.

📇

Truststore = Clint’s list of Cashs

When the app is the client. cacerts. GPO doesn’t touch it, so add our root by hand.

keytool -genkeypair ... -keystore conf/app-2026.p12 # Seb makes key in a NEW wallet keytool -certreq ... -file app-2026.csr # application to Cash keytool -importcert -trustcacerts -alias corp-root ... # Cash's cert first keytool -importcert -alias tomcat -file app-2026.cer # then Seb's ID, same alias
Same steps as IIS, different tools. "PKIX path building failed" means Clint (the Java app) doesn't know Cash: our root isn't in that JVM's cacerts. Vendor Java upgrades can wipe it. Full walkthrough on the Java and Tomcat page.

Java and Tomcat · renewal

Renewing Tomcat with keytool

# 1. New key + CSR in a NEW keystore, on the server keytool -genkeypair -alias tomcat -keyalg RSA -keysize 2048 \ -dname "CN=app.corp.local" -ext "SAN=dns:app.corp.local,dns:app01.corp.local" \ -keystore conf/app-2026.p12 -storetype PKCS12 keytool -certreq -alias tomcat -keystore conf/app-2026.p12 \ -ext "SAN=dns:app.corp.local,dns:app01.corp.local" -file app-2026.csr # 2. After the PKI admins sign it: CA first, then cert (same alias) keytool -importcert -trustcacerts -alias corp-root -file root-ca.cer -keystore conf/app-2026.p12 keytool -importcert -alias tomcat -file app-2026.cer -keystore conf/app-2026.p12 # 3. Check, point server.xml at it, restart, test, delete the old one keytool -list -v -keystore conf/app-2026.p12
"Failed to establish chain from reply" means you imported the cert before its CA. "PKIX path building failed" at runtime means the truststore is missing our root. Full walkthrough on the Java and Tomcat page.

Private keys

Why not to export them

📧

Copies spread

Shares, email, tickets, git, Downloads, backups.

🧨

Blast radius

One key on five servers: one breach leaks all five.

❓

We lose track

Can’t say where the key is, so can’t say it’s safe.

New server? New request, new key. Never export the old one.

If export is genuinely needed (web farm, appliance), agree it with the PKI admins, strong unique password sent separately, delete every copy.

A .pfx is cert plus private key. If a copy may have leaked, the only fix is revoke and reissue with a new key. Changing the pfx password doesn't help.

Almost every attack used old options left on “for compatibility”. That’s why we turn them off.

"SSL certificate" is just the name that stuck; certs are the same whatever protocol version uses them. Also worth a sentence: DigiNotar (2011), a CA that was hacked and used to fake Google certificates. A compromised CA can impersonate anyone, which is why our CA is so sensitive.

The long game

Save now, decrypt later

📼

Today

Record encrypted traffic. Cheap, silent, undetectable.

⏳

Wait

For a stolen key, or for the maths to break.

🔓

Later

Decrypt what was captured years ago.

Payroll, HR, legal, ratepayer and SCADA data stay sensitive for years. A breach in 2032 of data sent in 2026 is still a breach.

Also called harvest now, decrypt later. Two ways "later" arrives: the server's private key leaks (Heartbleed), or the public-key maths gets broken (quantum).

Later, version 1 · The key leaks

Heartbleed (2014): servers bled their private keys

💔 What happened

Bug in OpenSSL (CVE-2014-0160). A crafted heartbeat made servers return 64 KB of memory per request, no logs. Researchers pulled out private TLS keys within days.

📼 Why recordings mattered

With old RSA key exchange, the session secret was encrypted with Seb’s public key. Steal that private key later and every recorded session opens up.

Key exchangeSeb’s key stolen later
TLS_RSA_… (old TLS 1.2)❌ All recorded past traffic readable
ECDHE (TLS 1.3 / modern 1.2)✅ Past sessions safe: forward secrecy
The paint colours in ECDHE are ephemeral: picked fresh, thrown away. Stealing Seb's long-term key later doesn't recover them. Heartbleed is why forward secrecy became mandatory, and why TLS 1.3 removed RSA key exchange. Other lessons: patching wasn't enough, you had to replace the key, reissue and revoke. And OpenSSL was hiding inside appliances and vendor software. Windows SChannel wasn't affected, but Apache, PHP and appliances next to it were.

What’s coming

Shorter certs, more automation, new maths

📉

Shorter lifetimes

Public certs: 200 days now, 100 from Mar 2027, 47 from Mar 2029.

🤖

ACME / Let’s Encrypt

Free, automated certs since 2015. Manual renewal at 47 days isn’t a plan.

⚛️

Post-quantum

Traffic recorded today may be decryptable later. ML-KEM hybrids already in browsers. ASD: move off classic crypto by 2030.

Internal certs aren’t bound by the public limits, but if renewal is manual, it will eventually be forgotten.

Ask vendors about TLS 1.3 and post-quantum support in their roadmaps. Keep TLS libraries patched.

What we do about it

Five things for our servers

1

TLS 1.3 where possible. On TLS 1.2 allow only ECDHE suites; turn off TLS_RSA_….

2

Patch TLS libraries, including OpenSSL, Java and .NET bundled in appliances and vendor apps.

3

Key might have leaked? Replace it. New key, new cert, revoke the old. Never just patch.

4

Know where every cert and key lives, so the next Heartbleed is a list, not a hunt.

5

Ask vendors about post-quantum (hybrid ML-KEM) support and roadmaps.

Number 4 is where the CMDB work comes in: certificates and the software that terminates TLS should be in the inventory.
