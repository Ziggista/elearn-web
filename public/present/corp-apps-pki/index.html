Why it matters

The most dangerous button in IT

⚠️

Your connection isn’t private

Attackers might be trying to steal your information from app.corp.local

Back to safetyAdvanced → Proceed to app.corp.local (unsafe)

A real attack and a misconfigured server look exactly the same. Every time we say “just click through”, we train users to click through the real one.

This is the "why" for the whole session. A certificate warning on one of our systems is a fault, not a feature. Our job is to make sure warnings only ever appear when something is really wrong.
🙋 User: The payroll site says “not private”?
🧑‍💻 IT: Yeah just click Advanced → Proceed, it’s fine
😈 Attacker on the guest Wi-Fi: Thanks!
Same goes for curl -k, verify=False, TrustServerCertificate=True, and clicking Yes on the RDP "identity cannot be verified" prompt. They all skip the check that stops a middleman.

Basics · 2 of 3

A certificate is an ID card for a public key

🏛️

Our CA

Its root is pushed to every domain PC by GPO

→
🪪

Server certificate

“This public key belongs to app.corp.local until 17 Sep.” Signed by our CA.

Clients check four things: name (in the SAN), dates, chain to a trusted root, revocation. Every cert error is one of those.

The SAN (Subject Alternative Name) list is the only list of names browsers check. The old CN field is ignored. If users reach the service by three names, all three go in the SAN.

Basics · 3 of 3

Middlemen: why the checks exist

😈

Malicious

Rogue Wi-Fi, ARP spoofing, DNS poisoning, a hacked switch. They can see the traffic, but can’t produce a trusted cert for our server.

🛂

Ours, on purpose

Load balancers, reverse proxies, TLS inspection. They hold a key + cert the client trusts, so they move where the cert lives.

TLS makes middlemen harmless only if the client checks the certificate.

If outbound HTTPS from a server fails with a chain error, check whether something in the path re-signs traffic before blaming the vendor. Java and Linux tools won't trust our internal CA unless we add it.

Our internal CA can mint a trusted cert for any internal name. That’s why the PKI admins issue, and why nobody gets broad enrolment rights.

Mention who the PKI admins are and how to reach them (see crib sheet). The Web Server template lets the requester choose the names, so enrolment on it must stay tightly controlled.

How we issue

Getting a SAN certificate: five steps

1
Decide names

Every name people and systems use: app.corp.local, app01.corp.local…

2
Request on server

certlm.msc custom request, or certreq -new. Key not exportable.

3
Send .req

To the PKI admins. It holds only the public key and names.

4
Accept .cer

certreq -accept on the same server. Check for the key icon.

5
Bind, test, record

IIS / SQL / RDP, test from another machine, add to the CMDB.

The key point: the private key is created on the server and never moves. Only public things (the request and the certificate) travel.

How we issue · the repeatable way

certreq with an INF file

[NewRequest] Subject = "CN=app.corp.local" KeyLength = 2048 Exportable = FALSE MachineKeySet = TRUE ProviderName = "Microsoft RSA SChannel Cryptographic Provider" ProviderType = 12 RequestType = PKCS10 [EnhancedKeyUsageExtension] OID = 1.3.6.1.5.5.7.3.1 ; Server Authentication [Extensions] 2.5.29.17 = "{text}" ; SAN _continue_ = "dns=app.corp.local&" _continue_ = "dns=app01.corp.local"

certreq -new app.inf app.req → PKI admins → certreq -accept app.cer

Full INF with KeySpec and KeyUsage is on the "Our PKI" page. Keep the INF with the server's docs and renewal is a two-minute job.

Java and Tomcat

Java ignores the Windows store

🪪

Keystore = my identity

Private key + cert + chain. conf/app.p12. Secret.

🤝

Truststore = who I trust

CA certs only. $JAVA_HOME/lib/security/cacerts. Not secret.

GPO doesn’t touch Java. Our root must be added to cacerts by hand, and vendor Java upgrades can silently wipe it.

Prefer PKCS12 (.p12) over the old JKS format. Same goes for vSphere, Linux boxes and appliances: anything outside domain-joined Windows needs our root added manually.

Java and Tomcat · renewal

Renewing Tomcat with keytool

# 1. New key + CSR in a NEW keystore, on the server keytool -genkeypair -alias tomcat -keyalg RSA -keysize 2048 \ -dname "CN=app.corp.local" -ext "SAN=dns:app.corp.local,dns:app01.corp.local" \ -keystore conf/app-2026.p12 -storetype PKCS12 keytool -certreq -alias tomcat -keystore conf/app-2026.p12 \ -ext "SAN=dns:app.corp.local,dns:app01.corp.local" -file app-2026.csr # 2. After the PKI admins sign it: CA first, then cert (same alias) keytool -importcert -trustcacerts -alias corp-root -file root-ca.cer -keystore conf/app-2026.p12 keytool -importcert -alias tomcat -file app-2026.cer -keystore conf/app-2026.p12 # 3. Check, point server.xml at it, restart, test, delete the old one keytool -list -v -keystore conf/app-2026.p12
"Failed to establish chain from reply" means you imported the cert before its CA. "PKIX path building failed" at runtime means the truststore is missing our root. Full walkthrough on the Java and Tomcat page.
😎

Browser on a domain PC: “Internal cert? Trusted.”

😭

Tomcat after a Java upgrade: PKIX path building failed

“It works in the browser” proves nothing.

Add "re-import our root into cacerts" to every Java app's upgrade checklist, or point the app at a separate truststore that upgrades don't touch.

Private keys

Why not to export them

📧

Copies spread

Shares, email, tickets, git, Downloads, backups.

🧨

Blast radius

One key on five servers: one breach leaks all five.

❓

We lose track

Can’t say where the key is, so can’t say it’s safe.

New server? New request, new key. Never export the old one.

If export is genuinely needed (web farm, appliance), agree it with the PKI admins, strong unique password sent separately, delete every copy.

A .pfx is cert plus private key. If a copy may have leaked, the only fix is revoke and reissue with a new key. Changing the pfx password doesn't help.

One does not simply

🧙‍♂️

email the .pfx

Ask: has anyone got a .pfx sitting on a share or in their Downloads folder right now? No judgement, just delete it after the session and tell the PKI admins if it's in use somewhere.

A brief history

SSL to TLS 1.3 in one line

1995SSL 2.0broken
1996SSL 3.0POODLE 2014
1999TLS 1.0BEAST 2011
2006TLS 1.1retired 2021
2008TLS 1.2OK with ECDHE
2018TLS 1.3preferred

Almost every attack used old options left on “for compatibility”. That’s why we turn them off.

"SSL certificate" is just the name that stuck; certs are the same whatever protocol version uses them. Also worth a sentence: DigiNotar (2011), a CA that was hacked and used to fake Google certificates. A compromised CA can impersonate anyone, which is why our CA is so sensitive.

Major incident

Heartbleed (2014)

💔

The bug

OpenSSL leaked 64 KB of server memory per request. No logs. Private keys came out within days.

📼

Decrypt later

Recorded traffic using old RSA key exchange became readable once the key was stolen.

🔁

The lesson

Patching wasn’t enough: new key, new cert, revoke the old. Many only patched.

OpenSSL was hiding in appliances, load balancers and vendor apps. Windows wasn’t affected; plenty next to it was. Know where your TLS software lives.

Heartbleed is why forward secrecy (ECDHE) became mandatory: session keys are fresh per connection, so a stolen server key can't unlock recorded past traffic. TLS 1.3 removed RSA key exchange entirely.

What’s coming

Shorter certs, more automation, new maths

📉

Shorter lifetimes

Public certs: 200 days now, 100 from Mar 2027, 47 from Mar 2029.

🤖

ACME / Let’s Encrypt

Free, automated certs since 2015. Manual renewal at 47 days isn’t a plan.

⚛️

Post-quantum

Traffic recorded today may be decryptable later. ML-KEM hybrids already in browsers. ASD: move off classic crypto by 2030.

Internal certs aren’t bound by the public limits, but if renewal is manual, it will eventually be forgotten.

Ask vendors about TLS 1.3 and post-quantum support in their roadmaps. Keep TLS libraries patched.
